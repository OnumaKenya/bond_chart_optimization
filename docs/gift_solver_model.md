# 贈り物配分を整数計画でいい感じに解く話

ブルアカの「贈り物」、どの子に渡すか地味に悩みませんか。

手持ちの贈り物には限りがあるし、同じ贈り物でも渡す相手によって美味しさが違うし、
「あと少しで絆ランクが上がる子」と「上げても何も起きない子」が混ざってる。
適当に配るとなんかもったいない気がするけど、ちゃんと考えると頭がこんがらがる。

というわけで、この「贈り物配分」をコンピュータに丸投げして
**絆ボーナスの合計が最大になる配り方** を計算させることにしました。
中身は **混合整数計画問題（MILP）** という最適化問題として書いて、
SCIP というソルバーに解かせています。

この記事はそのモデルの解説です。実装は
[app/backend/gift_solver.py](../app/backend/gift_solver.py) の
`solve_gift_distribution()` にあります。

---

## まず、何が難しいのか

問題の前提をざっくり並べます。

- 生徒（衣装）には **絆ランク**（1〜50）がある。上がると絆ボーナスが増える。
- ランクを上げるには **経験値（EXP）** が要る。EXP は **贈り物** を渡して稼ぐ。
- 贈り物は在庫が有限。種類ごとに「何個持ってるか」が決まってる。
- 同じ贈り物でも、**渡す相手の「好み」によって獲得 EXP が変わる**。

で、ここがいちばん厄介なんですが、**絆ボーナスは階段状** なんですよね。
ランクそのものじゃなくて、ランクが属する「区間」で決まる
（[student.py](../app/backend/student.py) の `BOND_RANGES`）。

| 区間 | 絆ランク |
|------|----------|
| 1 | 2〜5 |
| 2 | 6〜10 |
| 3 | 11〜15 |
| 4 | 16〜20 |
| 5 | 21〜30 |
| 6 | 31〜40 |
| 7 | 41〜50 |

つまり、区間の境界をまたぐ瞬間までボーナスはゼロ。
「あと EXP ちょっとで次の区間に届く子」に渡せば一気に美味しいけど、
「区間の真ん中にいる子」に同じだけ渡してもしばらく無反応。

しかも贈り物は **早い者勝ちの共有資源**。A に渡したら B には渡せない。
「効率の良さそうな子から順に配る」みたいな貪欲なやり方だと、
境界の手前で止まる子に EXP を捨てちゃうんです。
ちゃんと先読みして全体で最適化しないといけない。だから最適化問題で書きます。

## モデルの中身

最適化問題は「変数・制約・目的」の3点セットで書きます。順番に。

### 変数：何を決めたいのか

```
x[g][c]      … 贈り物 g を衣装 c に何個配るか（0以上の整数）
delta[c][r]  … 衣装 c がランク r に到達するか（0 か 1）
```

`x` が「配り方」、`delta` が「その結果どこまで上がったか」。この2つを決めます。

### 制約：守らないといけないルール

**① 在庫を超えて配れない**

```
Σ_c x[g][c] ≤ qty[g]
```

贈り物 g を全員に配った合計が、持ってる数 `qty[g]` 以下。当然ですね。

**② ランクは飛び級できない**

```
delta[c][r] ≤ delta[c][r-1]
```

ランク r に到達してるなら、その下の r-1 にも到達してるはず。
途中をすっ飛ばして上のランクだけ立つ、みたいなズルを禁止します。

**③ 使った EXP は、稼いだ EXP の範囲内**

```
Σ_r e(r)·delta[c][r]  ≤  Σ_g v[g][c]·x[g][c]
       (使った EXP)            (もらった EXP)
```

左辺がランクアップで消費した EXP の合計、右辺が贈り物でもらった EXP の合計。
収入の範囲で支出する、という家計簿みたいな式です。

- `e(r)` … ランクアップに必要な EXP（[bond_exp.py](../app/backend/bond_exp.py)）
- `v[g][c]` … 贈り物 g を衣装 c に1個渡したときの獲得 EXP

### 目的：何を一番にしたいのか

```
maximize  Σ b_c(r)·delta[c][r]
```

到達したランクの絆ボーナスを全部足して、それを最大化。これがゴールです。

## ここがこのモデルの面白いところ

定式化、地味に工夫がいくつか効いてます。個人的にここが推しポイント。

### 工夫①：EXP を「お金」だと思って、贈り物とランクを直接つながない

制約③をもう一回見てください。**「どの贈り物がどのランクアップに使われたか」を
一切モデル化してない** んですよ。ただ「衣装 c の EXP 収支が黒字」と言ってるだけ。

なんでこれで OK かというと、EXP って **可換** だからです。
ゲーム内では EXP をいったんプールに溜めて、溜まった分だけ勝手にランクが上がる。
だから「この贈り物がこのランクアップ担当」みたいな個別対応を追う必要がない。

> 衣装ごとに「EXP 収入 ≥ EXP 支出」さえ守れば、
> あとは制約②（連続性）が「下のランクから順に埋まる」のを保証してくれる。

`x`（配り方）と `delta`（到達）を、EXP の総和という **不等式1本だけ** でつなぐ。
個別対応を持たないからモデルが軽い。これがこのモデルの背骨です。

### 工夫②：「その他」の贈り物はプールにまとめて変数を減らす

`v[g][c]` は本当は g×c のデカい表なんですが、実は
**ほとんどの贈り物は、誰に渡しても EXP が同じ** なんですよね。
好みに入ってない素の通常贈り物はどの子でも 20 EXP、高級なら 120 EXP。

なので入力を作る [callbacks.py](../app/frontend/callbacks.py) 側で、
贈り物を2グループに分けます。

- **個別贈り物**：好み・全体型・贈り物選択ボックス。相手によって価値が変わるやつ。
- **その他**：上記以外の素の通常／高級。誰に渡しても価値一定のやつ。

で、「その他」は **通常プール1個・高級プール1個の擬似贈り物** にガッと合体させる。
個数を全部足して、全衣装一律 EXP の1行として扱う。
これでソルバーが相手にする変数が「個別贈り物の数 + せいぜい2」で済む。
実データだとモデルがグッと小さくなります。

### 工夫③：同点なら「贈り物を温存する」— おまけ目的を重みで仕込む

目的が「ボーナス最大化」だけだと、実は答えが1つに決まらないんです。
EXP が中途半端に余ってもボーナスは変わらないから、ソルバーが
「使っても使わなくても結果同じ」な贈り物を気まぐれに突っ込んだ解を返してくる。
それはちょっと嫌。

そこで **おまけの目的：使う贈り物の総数はできるだけ少なく** を足します。
2つの目的を1本の式に畳んでこう書く。

```
maximize  W ×（絆ボーナス合計） − （使った贈り物の総数）
W = （全贈り物の所持数の合計） + 1
```

`W` は「贈り物を全部ケチっても、絆ボーナス1点には絶対に勝てない」ように
わざと大きくした重み。使う総数はどう頑張っても所持数の合計より大きくならないので、
ボーナスが1増える価値（`W`）が必ずそれを上回る。結果、

> **まず絆ボーナスを最大化。そのうえで同点なら、いちばん贈り物を使わない解。**

が自動で1つに決まる。「優先順位つきの最適化」を重み1本で表現する小技です。

### 工夫④：それでも同点なら、優先度の高い衣装に寄せる

工夫③で「ボーナス最大 → 使用数最小」まで絞っても、まだ答えが1つに決まらない
ことがあります。典型的なのは **同じ贈り物がどの子にも同じ価値** のとき。
A に渡しても B に渡してもボーナスも使用数も同じ、という完全な同点です。

こういうときは「どっちでもいい」ではなく、
**育てたい子（優先度の高い衣装）の絆ランクが上がるほう** を選んでほしい。
そこで UI 側で衣装を ▲▼ で並べ替えられるようにして（上が最優先）、
その順位を `costume_priorities` としてソルバーに渡します。

やることは **辞書式最適化**（lexicographic optimization）。
上位の目的の最適値を制約として固定してから、次の目的を解く、を繰り返します。

```
① maximize  W×(絆ボーナス合計) − (使用贈り物数)   … 工夫③の式
     → 最適値を制約として固定
② maximize  順位1グループの獲得ランク数の合計   → 固定
③ maximize  順位2グループの獲得ランク数の合計   → 固定
   …
```

ポイントは **①をまるごと固定してから②以降に進む** ところ。
絆ボーナス合計も使用贈り物数も①の時点でロックされるので、

> 優先度をどう付けても、**もらえるボーナスは減らないし、使う贈り物も増えない**。

余った贈り物が優先度の高い衣装に無駄に注ぎ込まれる、みたいなことは起きません。
あくまで「どうせ同じコストなら、こっちの子に寄せる」だけの誘導です。

同順位（同じ値）の衣装は1つのグループにまとめて同時に最大化。
順位を付けなかった衣装はタイブレークの対象外（末尾グループ）。
全衣装が同順位・全部未指定なら段が1つしかないので、
そのまま工夫③の1回きりの求解に戻ります。ムダな求解はしません。

なお、この辞書式のやり方は
「不足する贈り物選択ボックスの数を最小化する」ソルバー
（`solve_required_boxes()` の `box_priorities`）でも同じ形で使っています。
あちらは「総ボックス数を固定してから、順位が上の衣装のボックス不足を減らす」
＝ 所持贈り物を優先度の高い子から充当する、という向きです。

### 工夫⑤：「あと少しで上がる」状態にも対応する

実際にプレイしてると、絆ゲージが途中まで溜まってることがあります。
これは `remaining_exp` という引数で受け取って、
**最初のランクアップに必要な EXP だけ** をその値に差し替えます。

```
最初のランクアップの必要 EXP = clamp(残り EXP, 1, 満額)
```

2段目以降は普通に満額。`[1, 満額]` の範囲に丸めてるので、
0 とか負とか満額超えみたいな変な入力でもモデルが壊れません。
モデルの形は変えず、係数を1個すげ替えるだけで「途中から」が表現できる。

## なんで MILP なの？ 貪欲じゃダメ？

このアプリには別に、絆チャートを「Sidney 分解」でサクッと解くソルバーもあります
（[sidney_algorithm.md](./sidney_algorithm.md)）。
じゃあ贈り物配分もそういう賢いアルゴリズムでやればいいのに、
なんでソルバー任せの MILP なのか。

贈り物配分には、貪欲法やソートでは崩せない厄介ごとが **同時に** あるんです。

- **共有資源の取り合い**：1個の贈り物は1人にしか渡せない（割当問題）
- **階段状のごほうび**：EXP を積んでも区間境界をまたぐまで報酬ゼロ（非線形）
- **相手依存の価値**：`v[g][c]` が相手で変わる（好みの組合せ最適化）

これ全部入りだと、「効率いい順に詰める」では境界の手前で EXP を捨てちゃう。
ナップサックみたいな先読みが要る。
だったら素直に MILP で書いて、ソルバーの分枝限定法に任せるのがいちばん早くて正確。
実データ規模なら数ミリ秒で解けます。考えるより投げたほうが速い、というやつ。

## 余談：そもそも多項式時間では解けない

実はこの問題、多項式時間の **厳密** 解法は（P≠NP を仮定する限り）存在しません。
正確には **強 NP 困難** で、擬多項式時間の厳密解法すらない。

しかも面白いのは、難しさの正体が
**数の大きさじゃなく、共有資源の組合せ構造のほう** だってこと。

このモデルの数値、実は全部小さく抑えられてるんですよ。

- 絆ランクは 1〜50 の固定範囲
- 必要 EXP `e(r)` は固定テーブル（最大 1740、[bond_exp.py](../app/backend/bond_exp.py)）
- `remaining_exp` は `[1, e(r0+1)]` にクランプ（[gift_solver.py](../app/backend/gift_solver.py)）
- 衣装の累積必要 EXP は $\sum e(k)$ という固定定数で頭打ち
- `value[g][c]` も「残り必要 EXP を超えて渡しても無駄」なので実質定数で頭打ち

入力サイズに依存しない定数しかない。だから「ナップサック」や「3-PARTITION」みたいな
**大きな数を使う典型的な NP 困難帰着は、この問題には効かない** んです。
それでも強 NP 困難。なぜかというと、数を一切使わないグラフ問題がそのまま埋まるから。

### 最大次数 3 の独立集合からの帰着

最大次数 3 のグラフ $G=(V,E)$ の **最大独立集合**（強 NP 困難）を、こう写します。

| グラフ | → 贈り物配分 |
|--------|-------------|
| 辺 $e \in E$ | 贈り物タイプ1つ、`gift_qty = 1` |
| 頂点 $v \in V$ | 衣装1つ |
| `value[e][v]` | $e$ が $v$ に接続なら 1、そうでなければ 0 |
| 衣装 $v$ の最初の昇格必要 EXP | `remaining_exp[v] = deg(v) ∈ {1,2,3}` |
| `bond_bonuses[v]` | 最初の区間だけ 1、上は全部 0 |

最小の `e` が 15 なので `deg(v) ≤ 3` は確実にクランプの内側。すると、

- 衣装 $v$ が点灯する（ボーナスを取る）⟺ 接続辺の贈り物を $\deg(v)$ 個 **すべて** もらう
- 辺 $(u,v)$ の贈り物は数量 1 しかない → **隣接する $u,v$ は両方は点灯できない**
- 点灯した衣装の集合 = $G$ の **独立集合**

絆ボーナスの最大化が、そのまま最大独立集合の最大化になります。
使う数値は `value∈{0,1}`、しきい値 ∈{1,2,3}、`qty=1`、`bonus∈{0,1}` だけ。
全部小さい定数なのに NP 困難という、まさに「組合せのほうの難しさ」が露出した形です。

### 何が言えるか

- **多項式時間の厳密解法はない**（P≠NP 前提）
- **擬多項式時間の厳密解法もない**（強 NP 困難なので）
- 「実データで数ミリ秒」は入力が小さいだけ。
  最悪ケースに備えて 15 秒の制限時間と `timelimit` フォールバックを置いてある
- 工夫②のグルーピングは **可逆な前処理**（最適値を変えない）ので、
  これだけでは複雑性クラスは変えられない。実用上の高速化のためのもの

逆に、難しさの源は **共有資源の取り合い** に尽きるので、そこさえ壊せば多項式で解けます。
たとえば各贈り物の使い道が1衣装に限定されれば、衣装ごとに独立に解けて自明に多項式。
このモデルの厄介さは、結局のところ「なんで MILP なの？」で挙げた
共有・階段・相手依存の三つ巴を **同時に** 持っていることそのもの、というわけです。

## ソルバーまわりの小ネタ

[PySCIPOpt](https://github.com/scipopt/PySCIPOpt) 経由で SCIP を呼んでます。

- **時間制限は 15 秒**。実データなら一瞬で解けるけど、
  想定外に重い入力が来たとき UI が固まらないための保険。
- 時間切れになったら `timelimit` ステータスで **途中までの最良解** を返す。
  `optimal` でも `timelimit` でも、解が出てれば画面に表示します。
- `infeasible` とかそれ以外はエラー表示にフォールバック。
- 最終ランクは `delta` が 1 になってる数を数えるだけで復元できる。
  連続性制約のおかげで 1 は必ず下から連続して立つので、数えれば一発。

## まとめ

贈り物配分ソルバーのモデルを一言でいうと、

> **EXP を「お金」とみなして、「配り方 `x`」と「到達 `delta`」を
> 収支の不等式1本でつなぐ MILP。階段状の絆ボーナスを最大化して、
> 同点はおまけ目的で『贈り物の節約』に倒し、
> それでも同点なら優先度の高い衣装の絆ランクに寄せる。**

このモデルの面白さは、結局のところ

1. 贈り物→ランクの個別対応を **持たない**
2. 価値が一定の贈り物を **まとめる**
3. 優先順位つきの目的を重み1本に **畳む**
4. 畳みきれない好みのタイブレークは辞書式で **後ろに並べる**

という「持たない・まとめる・畳む・並べる」の4つ。
問題の構造をよく見ると、ソルバーに投げる前にここまで身軽にできる、という話でした。

### おまけ：記号表

| 記号 | 意味 |
|------|------|
| `x[g][c]` | 贈り物 g を衣装 c に配る個数（整数変数） |
| `delta[c][r]` | 衣装 c がランク r に到達するか（0/1 変数） |
| `qty[g]` | 贈り物 g の所持数 |
| `v[g][c]` | 贈り物 g を衣装 c に1個渡したときの獲得 EXP |
| `e(r)` | ランクアップに必要な EXP |
| `b_c(r)` | 衣装 c のランク r が属する区間の絆ボーナス |
| `W` | おまけ目的の重み（所持数の合計 + 1） |
| `costume_priorities[c]` | 衣装 c の優先順位（1 が最優先、同値は同順位、未指定は対象外） |
